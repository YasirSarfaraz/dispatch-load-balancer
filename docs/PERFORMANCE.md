OR-Tools' drop penalties are lexicographic by priority and count orders, so it first maximises the orders served per priority level and only then minimises distance. When the assigned counts match, the distance change is a like-for-like comparison.

**Priority check:** no OR-Tools result left a HIGH order unassigned while serving a lower priority.

| X-n110-k13 | 109 | 13 | 14,971 | ortools | 109 / 109 | 16,618 | +11.0% | 3,007 |

How the benchmark is run:
- Each `.sol` file is first re-evaluated and must reproduce the published cost exactly, which
  validates the parser, the node numbering and the metric.
- Every vehicle starts at the depot with capacity Q; every customer becomes an order with its demand
  as weight and the same priority. The fleet is max(k, routes in the BKS).
- Distances use the CVRPLIB EUC_2D metric (Euclidean, rounded per arc) through a test-only
  `DistanceCalculator`; costs are evaluated as closed tours (depot to depot), as CVRPLIB defines them.

Read the gap with care: production optimises **open** routes (no return leg), so both strategies
ignore the return legs the benchmark charges, and OR-Tools runs with the production settings
(greedy warm start, 3 s). Best-known solutions come from hours of specialised search.

## Methodology

- **Setup:** one `@SpringBootTest` (real application context, H2 in-memory) runs the scenarios in a
  fixed order on data from the production `TestDataGenerator` with a fixed seed. Both tables are
  cleared before each scenario, so every upsert inserts into empty tables.
- **Timing:** each figure is a single wall-clock run (`System.nanoTime`) after the JIT warm-up.
  Numbers vary between machines and runs; compare orders of magnitude, not milliseconds. OR-Tools'
  Guided Local Search always uses its full time limit.
- **Correctness:** every result is checked by assertions: the strategy that ran, one route per
  vehicle, no vehicle over capacity, loads and distances consistent with the stops, every order
  exactly once, valid unassigned reasons, and greedy's HIGH-priority invariant. Generous time
  thresholds fail the build if exceeded.
- **Memory:** a background thread samples used heap every 5 ms; "Peak heap" is the maximum sample
  (it includes the Spring context and uncollected garbage). OR-Tools allocates its solver memory
  off-heap, so that part is not included.
- **Database:** H2 in-memory is faster than a networked PostgreSQL; with the `prod` profile, add
  `reWriteBatchedInserts=true` to the JDBC URL to keep batched inserts efficient.
